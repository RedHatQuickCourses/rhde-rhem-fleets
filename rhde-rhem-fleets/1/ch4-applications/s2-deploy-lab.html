Lab: Deploy Applications to a Fleet

Estimated reading time: 10 minutes.

Objective

Deploy a containerized application to a device fleet and observe its rollout and operation.

Pending Review

Before you begin

You need a development machine running RHEL and hosting a few local VMs that stand in for managed devices. These local VMs are already provisioned and enrolled in Edge Manager.

You also need a server machine running RHEL, which is already configured as an Edge Manager server.

Both your development machine and server machine were configured by performing the first lab.

If you are using the course classroom, your development machine is the workstation VM. Log in as the user student with password student. From that machine, you may start SSH sessions to the servera VM, which is your server machine, using the same user. Alternatively, you can open a shell or a console directly on the servera VM.

This lab does not require the outcomes of any of the previous labs; you could complete only the first lab and skip to here. The example outputs of commands assume that you are performing all labs sequentially, in the same environment. If you skipped any of the previous labs, or if you had to destroy and recreate your environment, your actual outputs may display different sets of VMs, devices, and fleets, but that should not affect the expected outcomes of this lab.

Instructions

You will create a fleet that contains both inline and git configuration files, and, more importantly, a single-container application. Then you will join a device to the new fleet, verify that the application is running, and simulate unexpected application downtime.

The inline configurations provide credentials to access a private registry. The private registry, in turn, provides:

  • A bootc container image, which is ready to run containerized application using Podman;

  • An application container, which runs a simple PHP application.

The git configuration is not really necessary for this simplistic scenario; it just shows that you use multiple configuration providers on the same fleet resource.

The classroom environment has an issue which requires setting SELinux to permissive mode. This is something Red Hat does NOT advise doing to any production system, including developer machines and CI/CD servers.

On your development machine, perform the following before you attempt any lab in this course.

$ sudo setenforce Permissive

Note that SELinux is still in enforcing mode on your server machine and also on all test VMs which stand in for managed devices. Only your development machine needs SELinux set to permissive mode.

  1. On your development machine, verify that you have the prerequisites from the first lab. If any of the prerequisites are missing, please return to the first lab and ensure that you did not skip any steps.

    1. Verify that you have a clone of the course samples repository.

      $ cd
$ ls rhde-rhem-samples
antora.yml  config  enroll ...

    2. Verify that you have at least two local VMs.

      $ virsh list --all

------------------------

      $ virsh list --all

-------------------------

Domain 'edge-1' started
# repeat for the remaining VMs

    4. Give your local VMs a few moments to finish booting. Then, log in on Edge Manager as a non-administrator and verify that there are two managed devices, which are online and up-to-date.

      $ flightctl login -u student -p student https://servera.lab.example.com:3443

Login successful.
      $ flightctl get device
NAME                                                    ALIAS   OWNER            SYSTEM  UPDATED         APPLICATIONS
mpr39vjcj5fup095de4pqnld6h4snt2ud79g74p7spv5i00jjid0    edge-3  Fleet/store      Online  UpToDate        NoApplications

    5. If you devices keep displaying as offline for too long, it might be related to clock skew. In that case, stop each of your local VMs and return to the beginning of this lab.

      Clock skew prevents a device from synchronizing with Edge Manager, and is known to happen if your ROLE classroom is stopped without first shutting down local VMs on your development machine and later your VMs are restarted from saved state. 
      $ virsh destroy edge-1
Domain 'edge-1' destroyed
# repeat for the remaining VMs

  2. Build and publish a bootc container image that includes a container runtime.

    Remember that the enrollment image, which you used at the beginning of this course, provided only a minimum RHEL system with the Edge Manager agent. That image did not include Podman or any other container runtime, so any attempt to run managed applications will fail unless you first update your devices to a suitable system image.

    1. Create a temporary working directory, and copy example files to it.

      $ mkdir temp-managedapp
$ cd temp-managedapp
$ cp -r ../rhde-rhem-samples/managedapp/* .

    2. Review the Containerfile. It adds the container-tools meta-package, which includes Podman. It also includes the qemu-guest-agent, which should resolve clock skew issues of local VMs.

      $ cat Containerfile
FROM registry.redhat.io/rhel9/rhel-bootc:9.6
# To use the upstream packages:
#RUN dnf -y config-manager --add-repo https://rpm.flightctl.io/flightctl-epel.repo && \
#    dnf -y install flightctl-agent-1.0.2 && \
# To use local copies of the packages:
ADD rpms /tmp
RUN dnf -y install /tmp/flightctl*.rpm && \
    dnf -y install container-tools qemu-guest-agent && \
    dnf clean all && \
    systemctl enable flightctl-agent && \
    systemctl enable qemu-guest-agent && \
    systemctl mask bootc-fetch-apply-updates.timer
ADD domain.crt /etc/pki/ca-trust/source/anchors/
RUN update-ca-trust

    3. From the working directory of the enrollment image, copy some auxiliary files which you need to include in your bootc container image, such as the private registry CAs and SSH keys.

      $ cp ../temp-enroll/domain.crt .
$ cp ../temp-enroll/edge-key.pub .
$ cp -r ../temp-enroll/rpms .

    4. Log in to the Red Hat container registry, so you can pull the RHEL 9 base bootc container and build your new bootc container image.

      $ podman login registry.redhat.io
...

      $ podman build -t rhem-containers .

...
Successfully tagged localhost/rhem-containers:latest
b78ad6382056022b5430359c9a3ad488464c2c8466219113784611b355d28f17

    5. Log in to your private container registry and publish your new bootc container image there.

      $ podman login -u student -p redhat registry.lab.example.com:5000
Login Succeeded!
$ skopeo copy containers-storage:localhost/rhem-containers:latest docker://registry.lab.example.com:5000/rhem-containers:v1.0
...
Writing manifest to image destination

  3. Build and publish a container image that contains a PHP web application.

    1. Review the contents of the PHP application. It only displays the version of its PHP runtime.

      $ cat index.php
<?php printf ("Mock web app running PHP %s\n", phpversion()) ?>

    2. Build and publish your application container.

      $ podman build -t webapp -f Containerfile-webapp .
STEP 1/8: FROM registry.redhat.io/ubi9/ubi
...

$ skopeo copy containers-storage:localhost/webapp:latest docker://registry.lab.example.com:5000/webapp:v1.0

Writing manifest to image destination

  4. Create a fleet that uses the new bootc container and also defines a single-container application.

    1. Review the fleet manifest, which uses all three configuration providers covered in this course series, to demonstrate that you are able to mix them at your convenience.

      $ cat frontend.yaml
apiVersion: flightctl.io/v1beta1
kind: Fleet
metadata:
  name: frontend
spec:
  selector:
    matchLabels:
      role: frontend
  template:
    spec:
      os:
        image: registry.lab.example.com:5000/containerhost:v1.0
      config:
      - inline:
        - content: |
            REPLACE_WITH_OSTREE_AUTH_JSON
          path: /etc/ostree/auth.json
        name: bootc-registry-auth
      - inline:
        - content: |
            REPLACE_WITH_ROOT_AUTH_JSON
          path: /root/.config/containers/auth.json
        name: app-registry-auth
      - gitRef:
          path: /managedapp/config
          repository: webapp
          targetRevision: main
        name: webapp
      applications:
      - appType: container
        envVars: {}
        image: registry.lab.example.com:5000/webapp:v1.0
        name: httpd
        ports:
        - 80:8080

    2. Create an authentication file for the private registry, and add it to the fleet configuration. Notice it must be added in two places, because the container runtime and the bootc subsystems do NOT share the registry authentication files.

      $ podman login --authfile auth.json -u student -p redhat registry.lab.example.com:5000
Login Succeeded!
$ AUTH_JSON=$( jq -c . auth.json )
$ sed -i "s|REPLACE_WITH_OSTREE_AUTH_JSON|$AUTH_JSON|" frontend.yaml
$ sed -i "s|REPLACE_WITH_ROOT_AUTH_JSON|$AUTH_JSON|" frontend.yaml

    3. Review your fleet manifest and ensure it no longer contains any REPLACE markers.

    4. Review the repository manifest, which defines the webapp git repository referenced by the frontend fleet. It points to the course samples repository.

      $ cat webapp.yaml
apiVersion: flightctl.io/v1beta1
kind: Repository
metadata:
  name: webapp
spec:
  type: git
  url: https://github.com/RedHatQuickCourses/rhde-rhem-samples.git

    5. Apply the manifests to your Edge Manager server.

      The status of the fleet may be Unknown for a while, while Edge Manager fetches the configuration files from the Git repository. 
      $ flightctl apply -f webapp.yaml
webapp.yaml: applying repository/webapp: 201 Created
$ flightctl apply -f frontend.yaml
frontend.yaml: applying fleet/frontend: 201 Created
      $ flightctl get fleet frontend
NAME            OWNER   SELECTOR        VALID
frontend        <none>  role=frontend   True

  5. Join a managed device to the new fleet.

    1. Edit the edge-1 device manifest so its labels match the new fleet selector.

      Edit any existing label with key role. If there is no label with that key, add one. Also ensure you remove any label with key location, to prevent the device matching multiple other fleets from previous labs.

      $ UUID=$( flightctl get device -l alias=edge-1 -o name )
$ flightctl edit device $UUID
apiVersion: flightctl.io/v1beta1
kind: Device
metadata:
  ...
  labels:
    alias: edge-1
    rhel: "9.6"
    type: noapps
    role: frontend
  name: 1u63hvsgtua9tjjbmla9bgh5h2s77cb8esepphnf68m3ocf8qfng
  ...
spec:
...
device/1u63hvsgtua9tjjbmla9bgh5h2s77cb8esepphnf68m3ocf8qfng edited

    2. Wait until the device status changes to UptoDate. Notice that the device now displays a Healthy status in the APPLICATIONS column, instead of NoApplications.

      $ flightctl get device $UUID
NAME                                                    ALIAS   OWNER           SYSTEM  UPDATED         APPLICATIONS
1u63hvsgtua9tjjbmla9bgh5h2s77cb8esepphnf68m3ocf8qfng    edge-1  Fleet/frontend  Online  UpToDate        Healthy

    3. Open another terminal and open a SSH session to your edge-1 VM. Verify that you get the expected "message of day"; proving that the device got the settings from the git configuration provider. Keep that SSH session open, as you will return to it.

      $ cd temp-managedapp
$ ssh -i ../temp-enroll/edge-key -p 8122 core@127.0.0.1
Managed device running a containerized web app

Last login: Wed Mar 11 19:30:01 2026 from 172.25.250.254
[core@enroll ~]$

  6. Verify the application is accessible, then simulate downtime in the application to show how Edge Manager reacts.

    1. On your development machine, access the mock of your web application.

      $ curl 127.0.0.1:8108
Mock web app running PHP 8.0.30

    2. On your edge-1 VM, find the container id of the application container and stop it.

      Remember that the password for the core user is redhat123. 
      $ sudo podman ps
CONTAINER ID  IMAGE                                      COMMAND               CREATED         STATUS         PORTS                 NAMES
ac31d8eae297  registry.lab.example.com:5000/webapp:v1.0  /bin/sh -c php-fp...  12 minutes ago  Up 12 minutes  0.0.0.0:80->8080/tcp  systemd-httpd-317337-app
      $ sudo podman kill ac31d8eae297
ac31d8eae297

    3. On your development machine, wait until Edge Manager reports a change in application status.

      $ flightctl get device $UUID
NAME                                                    ALIAS   OWNER           SYSTEM  UPDATED         APPLICATIONS
1u63hvsgtua9tjjbmla9bgh5h2s77cb8esepphnf68m3ocf8qfng    edge-1  Fleet/frontend  Online  UpToDate        Error

    4. Verify that your web application is indeed offline.

      $ curl 127.0.0.1:8108
curl: (56) Recv failure: Connection reset by peer

    5. After a few moments, Edge Manager restarts the container and the application status is back to healthy.

      $ flightctl get device $UUID
NAME                                                    ALIAS   OWNER           SYSTEM  UPDATED         APPLICATIONS
1u63hvsgtua9tjjbmla9bgh5h2s77cb8esepphnf68m3ocf8qfng    edge-1  Fleet/frontend  Online  UpToDate        Healthy

    6. If you wish, you can verify that the application is again accessible and a new container is running on the managed device. You can now close the SSH session on your edge-1 VM.

You demonstrated that Edge Manager can deploy, monitor, and keep containerized applications running on managed devices. This gives organizations the flexibility of managing application lifecycles independently of operating systems updates, if they wish.
